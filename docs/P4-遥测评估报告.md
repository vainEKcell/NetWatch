# P4 底层网络遥测评估报告

> 结论先行：**当前 ETW 方案保留为主干**。它已覆盖本工具分析目标所需信息的约九成，且零驱动、零外部依赖。
> WFP 内核驱动方案明确否决（成本/风险与收益不成比例）；Sysmon 做成"存在即增强"的可选集成；防火墙审计日志（5156/5157）作为轻量中间路线备案。

## 一、现状盘点：当前 ETW 方案能拿到什么

| 数据 | 来源提供程序 | 质量 |
|---|---|---|
| 每进程收发字节（含重传）、本机/远端地址端口、方向 | 内核 `NetworkTCPIP`（TcpIp/UdpIp Send/Recv/Retransmit） | 实时、可靠、进程级 |
| 新连接 / 断开事件 | `TcpIpConnect/Disconnect`（v4+v6） | 实时 |
| 每进程 DNS 查询与解析结果（含缓存命中） | `Microsoft-Windows-DNS-Client` 3008 | 实时；不含 DNS 服务器地址 |
| 进程生命周期、父进程 PID、完整命令行 | 内核 `Process`（Start/DCStart/Stop，含会话 rundown） | 实时；DCStart 覆盖启动前进程 |
| 连接表瞬时快照（含 LISTEN 暴露面、UDP 绑定） | iphlpapi（`TCP_TABLE_OWNER_PID_ALL=5`） | 2 秒轮询 |
| 服务归因（PID→服务名） | advapi32 `EnumServicesStatusEx` | 30 秒刷新 |

**已知盲区**：无用户/SID 上下文；无防火墙裁决（允许/拦截）信息；DoH 绕过系统解析器；字节数为内核事件口径（≈IP 层负载）与网卡计数有合理偏差；svchost 需借助服务枚举做二次归因（已做）。

## 二、候选方案逐项评估

### 1. WFP（Windows Filtering Platform）ALE 层 —— 否决（现阶段）

- **能多拿到什么**：权威的每连接应用路径（内核级防伪装）、用户 SID、防火墙裁决（permit/block）、精确方向、每连接生命周期（AUTH_CONNECT → FLOW_ESTABLISHED → CLOSED）。
- **为什么贵**：向用户态**流式**输出 WFP 事件必须写内核 Callout 驱动（KMDF/WDM）。代价清单：
  - 驱动签名（分发需微软 attestation 签名，开发期要开测试模式）；
  - 蓝屏风险直接进内核，质量门槛高；
  - 安装/卸载一个驱动服务，杀软常对无名驱动告警（与"分析工具要低摩擦"矛盾）；
  - 需处理与第三方安全软件（同样挂 WFP callout）的共存问题。
- **用户态替代不成立**：FwpmOpenSession 等 API 只能管理过滤规则与枚举状态，**不能**把连接事件推给用户态；`netsh wfp capture` 是重型会话式抓取（XML 事后分析），不适合常驻实时监控。
- **重启条件**（满足其一再评估）：① 用户 SID 归因成为硬需求；② 需要防火墙裁决的权威关联且 5156/5157 审计方案（见 3）不敷使用；③ 出现伪装路径绕过文件级身份的真实案例。

### 2. 防火墙审计日志（安全日志 5156/5157）—— 备案的轻量中间路线

- **是什么**：开启审核策略后，Windows 会把 WFP 的"允许连接(5156)/拦截(5157)"写进安全事件日志，含 PID、应用路径、方向、源/目标地址端口。
- **优点**：**零驱动**；EventLogWatcher 实时订阅即可；能补上当前最大的盲区——"这条连接被防火墙放行还是拦截了"。
- **缺点**：默认审核策略不开启（需 `auditpol /set /subcategory:"Filtering Platform Connection" /success:enable`，属系统级改动需明示用户）；事件量大；不含命令行/用户（需与现有数据按 PID 关联）。
- **建议**：作为可选功能（默认关，设置页给开关并说明影响）。本次未实现，属增量改动，随时可加。

### 3. Sysmon（Event ID 3 网络连接 + 1 进程创建）—— 做成"存在即增强"

- **能多拿到什么**：**用户名/SID**、`ProcessGuid`（完美 lineage，彻底解决 PID 复用归档）、`Initiated`（主动/被动方向）、进程创建全字段（Hashes、ParentImage）。
- **前提**：机器上已由用户自行安装并运行 Sysmon（微软 Sysinternals，第三方依赖），读取 `Microsoft-Windows-Sysmon/Operational` 日志通常需管理员。
- **集成设计**（若做）：启动时探测该日志通道是否存在 → 存在则 `EventLogWatcher` 订阅事件 3，按 PID/ProcessGuid 与现有事件流做富化（User 字段进详情面板与证据链）；不存在则静默降级，功能不受损。
- **建议**：列入可选增强（P4.5），不作为依赖。

### 4. 其他 ETW 提供程序 —— 维持现状

- `Microsoft-Windows-TCPIP`（TCP 状态机内部细节）：对行为分析增益边际，噪声大。
- DNS-Client 3006（查询发起）：可测解析延迟，属锦上添花。
- 结论：当前 `NetworkTCPIP + Process + DNS-Client` 的组合是对的，不扩。

## 三、决策矩阵

| 维度 | 现有 ETW | +防火墙审计(5156/7) | +Sysmon | WFP 驱动 |
|---|---|---|---|---|
| 额外依赖 | 无 | 系统审核策略改动 | 需预装 Sysmon | 自研内核驱动 |
| 用户 SID | ✗ | ✗ | ✓ | ✓ |
| 防火墙裁决 | ✗ | ✓ | ✗ | ✓ |
| 进程身份强度 | 路径+签名+命令行 | 同左 | +ProcessGuid+Hash | 内核级应用路径 |
| 实现成本 | 已完成 | 低 | 中 | 极高 |
| 稳定性风险 | 无 | 低 | 低 | 高（蓝屏面） |

## 四、最终建议

1. **保持现有 ETW 主干不变**（本轮决策）。
2. 观察实际使用中是否真的出现"盲区挡住分析"的场景（例如用户追问"这条连接是放行的还是被拦的"），是则优先实现 5156/5157 订阅（改动小）。
3. Sysmon 增强做成探测式集成，放到允许名单/处置体系稳定之后。
4. WFP 驱动仅在出现真实的"文件级身份被伪装绕过"案例时重启评估。
